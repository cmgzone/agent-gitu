# Browser and Google sign-in

The computer button in a teammate's chat opens its browser inside the conversation when the teammate uses the host computer. Code chat's Browser action also opens an interactive card in the conversation. Expand fills the app without opening another browser window. Android uses the same authenticated viewer as desktop and hosted clients; this UI update does not require a new APK.

## Sign the Chrome browser itself into Google

Open the browser's **⋯ → Your Chrome profile**. Choose **This hosted server**, a saved cloud computer, or local Docker, then **Open Google Chrome**. This opens a full, regular Google Chrome desktop inside the chat, including Chrome's own profile menu. Use that menu to sign into your Google account and optionally enable Chrome sync. Complete passwords, verification codes, passkeys and account prompts directly in Chrome. This does not need the Gitu Google OAuth client described below.

The full Chrome profile requires an **AMD64 Linux computer server** with the Gitu desktop runtime. The desktop image installs official Google Chrome on AMD64; the ARM64 Chromium fallback cannot provide Google Chrome profile sync and is rejected for this feature. The hosted app connects through its private desktop broker; a saved SSH cloud computer also works. A bare hosted web process without a computer runtime cannot run the full Chrome desktop. Initial startup can build the desktop image. Local Windows installations without Docker can choose a saved cloud computer instead.

This computer is private to the owner by default, separate from every teammate's assigned computer and automated browser. Its Chrome profile is kept in a persistent home volume on the selected server. Stopping the session or restarting Gitu keeps the profile. Switching servers does not transfer Google credentials or sync data between servers. Users remain subject to Google's normal account security and sync policies; complete passwords and verification privately.

To let P.A continue a website task in this **same signed-in Chrome window**, choose P.A and the direct chat under **Continue with your teammate**, then press **Return to P.A**. This explicitly grants that teammate's chosen chat access through `desktop_screenshot` and `desktop_input`, and wakes it to continue the existing request. Its regular `browse`, file and shell tools keep using its assigned computer. No browser profile files, cookies or DevTools connection are supplied through the handoff. Company agents and temporary helpers cannot inherit it; the personal teammate must have desktop/shell permission.

Use **Take private control** before entering passwords or completing verification. This revokes the grant, aborts in-flight desktop actions and discards observations that finish after control changes. Return to P.A again when ready. Logout, session expiry, permission loss and app restart also revoke the grant. Closing the viewer does not itself revoke a handoff; take private control or sign out when you want to end access.

Teammates receive computer identity metadata so they can distinguish the installation host, their assigned Linux desktop and the owner's separate Chrome session. `computer_status` identifies an active handoff or the assigned computer explicitly; a connected browser does not establish VPS access or website sign-in. Metadata alone never grants control or exposes pages, cookies or credentials, and company agents cannot see the owner's private Chrome location. The structured Agent browser and regular desktop Chrome have separate profiles; teammates inspect the shared desktop to establish its current website state.

The Chrome view includes private typing controls for mobile. Use **Zoom** for larger desktop controls, **Pan** to move around the enlarged desktop, and turn Pan off to click. **Fit** returns to the whole desktop. **Back to agent browser** keeps Chrome open; **Stop** releases the running computer while retaining its profile. Existing owner authentication, HTTPS/WSS or SSH transport, and logout/session-expiry revocation protect the viewer.

### Use the computer from a touchscreen

Phone and tablet viewers show a touch toolbar with **Zoom**, **Pan**, **Keyboard** and **Help**. Tap to click, hold to right-click, drag an item with one finger, and drag with two fingers to scroll. Zoom switches to the desktop's full resolution with Pan enabled so a one-finger movement moves your view. Turn Pan off to click or drag items, or press Fit to see the whole desktop again. These controls adjust the viewer without resizing or restarting the remote desktop.

Tap a field in the desktop, then **Keyboard** to use the phone keyboard. This takes private control and pauses the agent before enabling Send. Text is masked, supports phone composition/IME input, and clears after sending; it goes through authenticated owner input controls rather than chat, model history or clipboard synchronization. Tab, Enter, Backspace, Escape and Address shortcuts are included. Control changes, disconnects, backgrounding and closing the viewer clear private drafts. Closing Keyboard leaves you in private control until you explicitly return it.

The regular desktop dialog fills the mobile viewport, keeps its control button reachable, and adjusts when the phone keyboard changes the available height. Chrome's teammate/chat choices collapse on touchscreens to leave room for the desktop. The same viewer serves local Docker, SSH and hosted computers, including Android's installed app; no APK rebuild is required for these server UI changes.

## Work across the installation computer and SSH server

A personal teammate with shell access can combine both computers in one task. Its ordinary file tools and `run_command` stay on the assigned computer; `ssh_exec` takes the exact saved connection ID and runs on that server. `computer_status` and the turn instructions list available saved SSH targets without exposing credentials or opening connections. SSH results identify the server used. Remote files can be inspected or changed through authorized SSH commands; this does not silently move local files, change the default computer, or transfer sign-ins. Coding remains Main Agent Gitu's responsibility and deployment follows the existing owner instructions. Company agents cannot use the owner's personal SSH credentials.

P.A can therefore inspect a local project, check a remote deployment over SSH, and operate the explicitly shared VPS Chrome in the same conversation. On hosted Gitu, “installation computer” means the hosted server; it does not grant access to a disconnected personal PC or Android filesystem.

These capabilities use the shared Cowork tool layer for all supported providers, including native function calls and the structured-text fallback. They do not require a Codex subscription. Visual Chrome operation requires a model that can interpret screen images; changing provider does not change the owner handoff or tool permissions.

The browser runs on the Gitu server in a dedicated persistent profile per teammate (and per company). It does not share the user's normal Edge/Chrome profile or Gitu's app-login cookies. Windows can use installed Edge with a separate Gitu profile when Playwright Chromium is unavailable. The hosted Docker image already installs Chromium and its dependencies. Bare Node installations need the matching Playwright Chromium and system dependencies installed by the server administrator.

Take control before interacting or signing in. The agent's browser tools stop accepting actions, screenshots and page evaluations until Return to agent is pressed. In-flight observation results are discarded if control changes. The owner's viewer continues to work, without page-text digests sent to the model. Typed text is masked and cleared after sending. Closing a viewer does not give control back automatically; the control preference survives server restarts.

This pauses browser tools, not arbitrary host shell access. A teammate granted broad host-file or command permissions still has those permissions. Use the existing private computer and permission controls when OS isolation is required. Use HTTPS for passwords on hosted servers; opt-in LAN HTTP remains unencrypted.

## Enable Google sign-in to Gitu

1. In Google Cloud, configure an OAuth consent screen and create an OAuth client of type **Web application**. Add test users if the consent screen is in testing.
2. Register the exact redirect URI `https://YOUR-GITU-HOST/auth/google/callback`. For local desktop development, Google permits a loopback URI such as `http://localhost:8321/auth/google/callback`. Private LAN HTTP addresses are not supported for Google sign-in.
3. Sign in to Gitu with the existing workspace owner email/password. Open **Settings → General → Account → Configure Google sign-in**, enter the public origin, Google client ID and client secret, then save. Changes apply immediately and survive restarts. Configure locally on the Gitu computer or over authenticated HTTPS. The client secret is stored only on the server and is never returned by the settings API.
4. Use **Link Google account** for the same owner email, then use **Sign in with Google** on the sign-in screen. Google cannot create or replace the first workspace owner. Non-Gmail addresses without a verified Google Workspace domain must be linked from a password-authenticated session first. Linking pins Google's stable account subject as well as the owner email.

Hosted deployments can instead configure `AGENT_GITU_GOOGLE_CLIENT_ID`, `AGENT_GITU_GOOGLE_CLIENT_SECRET`, and `AGENT_GITU_PUBLIC_ORIGIN=https://YOUR-GITU-HOST` using their deployment secret manager. Saved Account settings take precedence. Keep `AGENT_GITU_TRUST_LOCAL_PROXY=1` only for a trusted loopback reverse proxy terminating HTTPS; the supplied Docker/nginx deployment already uses that arrangement. Gitu requires a trusted HTTPS certificate on Android.

Google authentication opens the system browser because embedded user agents are restricted by Google's OAuth policy. After verification, return to Gitu: a one-time completion secret held only by the initiating app exchanges the verified result for its normal eight-hour session. The system browser does not receive the Gitu app session. The flow uses one-time state, PKCE, nonce, Google signature/issuer/audience/expiry verification, ten-minute expiry and same-origin initiation/completion. It requests only `openid email profile`; Google access/refresh tokens are not stored.

Signing into websites in the chat browser uses those websites' own login pages and the server's isolated browser cookies. Website support varies: Google and other providers may reject automated browsers. Gitu does not spoof user agents or bypass provider restrictions. The existing private computer's regular Chrome browser remains available for sites requiring a full interactive desktop. Gitu's own Google sign-in does not sign the chat browser into Gmail or grant mailbox access.
