# Cowork coding handoffs

Cowork teammates hand repository implementation, debugging, builds and tests to Main Agent Gitu with `gitu_task`. The brief should include the requested outcome, repository location, constraints and acceptance checks. `projectPath` selects a saved project, the current workspace, or a folder attached to the conversation; company projects stay inside their company workspace.

Every accepted handoff creates a persistent task in the main Code workspace, linked to its requesting teammate, conversation, company and mission. Code navigation lists these under **Cowork coding**, and Cowork shows a **View coding task** button. Users can message the coding agent directly in Code; the teammate receives an awareness note without delegating the instruction again. Attachments follow the coding instruction. The interface stays in Code, including when a private computer needs a new runtime after restart. Paused companies must resume before accepting follow-ups.

Chat handoffs return a running-task handle immediately, so P.A and other teammates remain available for other tasks. Mission handoffs still await a verified result. Completion or failure is saved immediately in the originating Cowork conversation and wakes the requesting teammate. Busy teammates receive live guidance and a durable inbox entry; company notifications use the company job queue. The teammate reports verified results to the user.

The requesting teammate's chat shows a coding task card with flowing water waves beneath its messages. The waves follow the teammate's colour. Tap or click the card to open the coding task in the same app. Its status follows the real coding session even while the teammate is idle or doing other work. Approval and question waits, model waits, completion, failure and stopping all stop the working animation. Reduced motion preferences disable the animation. Cards remain available after reconnecting; tasks from other conversations or companies stay outside the view.

Local tasks use the main Gitu coding runtime and saved model choice. Plan reviews, questions and approvals share the same authority across Code and Cowork. Approving a coding card in either view resolves the same gate and records approval in the other. The delegated chief approves routine project checks under the existing authority policy, and Cowork records who approved them. Destructive operations, production deployment, credential access and external writes still require the owner. Stop cancels the same task.

A coding failure asks the requesting teammate to diagnose a concrete repair and submit `gitu_task` with `retryOf` and a specific repair goal. Recovery stays in the original project, computer, conversation budget and permission scope. At most two repairs are allowed, and duplicate requests reuse the existing recovery task. Repeated identical errors, missing credentials/access/billing/approvals and exhausted repairs create a **Coding needs your help** card. User-stopped and completed tasks cannot restart automatically.

Private-computer tasks remain on their assigned private/cloud computer. Main Agent Gitu owns the visible task and supervises a permission-scoped execution worker on the requesting teammate's computer. Company tasks use this scoped worker even when the owner granted company host access, retaining the company's approved models, tools and connections. That worker retains the existing budget and evidence checks and reports back through the same handoff. A missing private runtime blocks the task; it does not move code onto the host. Private worker file/check details remain in its execution report rather than being invented as local files or local checks.

Source-code writes and common developer commands from a durable Cowork teammate return a handoff instruction. Ordinary document work remains available. Delegation does not grant additional permissions or budget.

The model chooser saves the latest explicit provider/model choice in `Settings/runtime-selection.json`. New main coding tasks and their scoped execution workers use this selection; choosing another model changes future tasks without replacing an active request. Alibaba remains available when explicitly selected and is excluded from automatic provider discovery. An unambiguous project folder named in a coding brief is preferred over the general workspace; company folder boundaries still apply.

Chiefs of staff have `app_manage` controls for app preferences, the default model and project, teammate models, internal messages and task follow-ups. They can list and delete requested agents, conversations, tasks and companies by exact ID. Removing a company first pauses its activity, stops its computers, saves a recovery snapshot under the company store's `Deleted` directory and retains project files. Chiefs cannot remove themselves or other chiefs; company chiefs remain scoped to their company. Credentials, security grants and approvals keep their existing controls.

Every coding attempt in the app, including a follow-up or Cowork handoff, saves a file checkpoint before running the coding engine. Failed and stopped attempts keep their checkpoint too. **Checkpoints & rollback** in the task view lists them and restores a selected checkpoint after coding stops. The chief can use `list_checkpoints` and `rollback_task` for the same controls. A restore first saves a recovery checkpoint, refuses to overwrite later edits to affected files, clears the stale completion report and starts a fresh verification phase. Git history and staging remain untouched by file rollback.

Checkpoints include pre-existing dirty files, untracked files, binary files and deletions. Dependency/cache directories, `.git`, `.hermes`, `.qa`, and embedded `browser-profiles` are excluded. Live browser profiles contain locked databases and private runtime state; they are also excluded from code indexing. A locked project source file still blocks the checkpoint and identifies the affected path. A checkpoint exceeding 2 GB or 100,000 project files blocks coding before the engine edits files; select the actual project folder instead. Local checkpoints live under `Sessions/coding-checkpoints`; private/cloud checkpoints stay on the assigned computer under `/workspace/.hermes/coding-checkpoints`. If a crash prevents the final file state from being recorded, automatic rollback refuses that unsealed snapshot because later edits cannot be distinguished safely.

Startup/checkpoint failures remain failed when the delegation releases its runtime. An unstarted runtime cannot overwrite that failure with its initial state. Cowork receives one notification per finished attempt; a running task never produces a completion notification. Retrying after the blocker is corrected starts real coding work and retains the normal checkpoint and permission gates.

The session-history database uses SQLite WAL and a bounded busy timeout so history readers can remain open while coding events, typed frames and final status are saved. Reading task history must not abort a coding turn with a database-lock error.
