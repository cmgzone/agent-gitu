# Mailbox sign-in recovery

On 21 October 2026, a read-only check of the configured Composio owner found four expired Gmail connections and three active Gmail connections. The provider's reasons identified all four expired entries as sign-ins that were not completed within the hosted link's time limit. No message content or credentials were logged, and no email was sent. This does not establish live delivery for the active connections or prove that different connection IDs represent the same upstream mailbox.

Gitu previously discarded the status reason and displayed all expired entries as needing reconnection. It assigned the connection ID when generating a link, so unfinished sign-in attempts remained alongside active connections. The Connected list offered only removal, while sign-in from Available required manual refresh.

The adapter now translates recognized initiation timeouts to the fixed `connectionIssue: "sign-in-expired"` classification without exposing raw provider reasons. Other expired authorization retains its reconnect status. Agent context explains that an unfinished sign-in does not invalidate a separate active connection, while preserving explicit mailbox selection.

The Connected list shows a fresh sign-in action alongside inactive accounts and distinguishes unfinished sign-in attempts. Counts include active, enabled accounts. Starting sign-in keeps a Continue sign-in link and checks the exact newly created account every 2.5 seconds. Another active mailbox cannot complete that flow. The page handles temporary status failures without claiming disconnection, rejects stale results after switching teammates or leaving the page, and offers a fresh sign-in after the ten-minute link lifetime. Unchanged polls preserve the current form and focus. Account assignments, grants, review requirements, and email retry behavior are preserved.

Provider guidance: [connected-account lifecycle and identity](https://docs.composio.dev/kb/guide/platform-connected-accounts), [manual authorization](https://docs.composio.dev/docs/authentication/manually-authenticating). Composio's deprecated `refresh` endpoint is not used; each user-triggered retry uses the existing `session.authorize` flow.

Validation includes 119 passing provider, route, account-awareness, native-mail, company-account and UI checks, production-UI browser checks at desktop and mobile widths, TypeScript build and targeted lint. The mobile browser check also caught and verified a fix for an invalid container query that prevented the account list from switching to one column. Evidence is recorded under `.qa/mail-sign-in-*.json`; browser checks use mocked sign-in and never contact a real mailbox. Real consent completion and live email delivery remain unverified.

The compiled fix is staged in `release/question-replies-preview/win-unpacked/Agent Gitu.exe`, alongside the preceding coding-agent reply fix. The preview manifest records passing checks and module hashes. The released 0.4.13 installers are unchanged. Use the tray's **Quit Agent Gitu and stop agents** before opening the preview so an older background engine is not reused. In Settings → Apps & accounts → Connected, select the intended teammate and use **Sign in again** beside an unfinished account. Complete provider sign-in promptly; the page confirms the exact resulting connection. Existing active accounts can also be assigned explicitly to another teammate through Existing accounts.
